Stenslee Studio

How the studio dashboard works

Every feature, step by step: what happens, which file runs it, what data changes and what the user sees. Tables and rules: database.md. Architecture and approach: technical.md.

Tattoo studios use dashboard.stenslee.com. A designer finds or adds a customer, creates tattoo designs with AI, shows a realistic preview on the customer's body and prints a stencil. The admin also runs the team, the design library, WhatsApp messages and deleted work. Customers never log in — staff act for them in the studio.

Studio adminEverything a designer does, plus team, dashboard, library, WhatsApp and trash.
DesignerCustomers, AI designs, previews and stencils. Sees only the sessions they handled.
CustomerNever logs in. Name, verified number and tattoo photos are saved per studio.

Login & signup

Staff log in with a code sent on WhatsApp. New studios sign themselves up. Each account is signed in on one device at a time, for at most 72 hours.

Log in existing staff

  1. The person opens the login page

    The proxy runs first. A logged-in, valid staff member is sent straight to their dashboard; anyone else sees the form. The page reads ?error= to show messages like "signed in on another device".

    proxy.ts → proxy(), login/page.tsx → LoginForm
  2. They type their mobile number

    The country picker defaults to +91. The number is checked: India needs 10 digits, other countries 4–14, and the full number at most 15 digits.

    <PhoneInput>, handleSendCode() → isValidPhone()"Enter a valid phone number."
  3. The page asks Supabase for a code

    Supabase is asked to start a phone login, and told never to create a new account here.

    supabase.auth.signInWithOtp({ phone, shouldCreateUser: false })unknown number → "This number isn't registered…"
  4. Supabase calls Stenslee's hook

    Instead of sending an SMS, Supabase POSTs the user id, phone and code to the hook. The hook checks the signature, then allows the code only for an active, non-removed staff member or a number with a signup started in the last 15 minutes.

    api/auth/send-whatsapp-otp → isValidSupabaseSignature(), isAllowedToLogIn()reads staff, signup_requests
  5. The code goes out on WhatsApp

    The code is sent from Stenslee's own WhatsApp number using an Authentication template. Refusals are answered with HTTP 200 and an error body, because that is the only way Supabase shows the message.

    sendAuthOtp() → sendTemplateMessage() in graph.tscode step with a 60-second resend timer
  6. They type the code and Supabase checks it

    A correct code creates the login session cookie sb-cleopatra-studio-auth.

    handleVerify() → verifyOtp({ phone, token, type: "sms" })"Incorrect or expired code."
  7. The page checks the staff row

    Role, active flag and removal are read. A deactivated or removed person is signed out again.

    reads staff role, is_active, deleted_at"Your account has been deactivated…"
  8. This device becomes the only device

    claim_staff_session() writes this login's session id into staff.current_session_id and stamps last_login_at; then every other device is signed out.

    supabase.rpc("claim_staff_session"), signOut({ scope: "others" })writes staff.current_session_id, last_login_at
  9. The right dashboard opens

    Admins go to /studio/admin, designers to /studio/designer (or back to ?next=).

    router.push(dest)dashboard

Sign up a studio self-serve

  1. The person fills in the signup form

    Usually from the website's "Get started free" button. Fields: studio name, your name, email, mobile number. The browser checks each field first.

    signup/page.tsx → handleSendCode()"Enter a valid email address."
  2. The server checks the number is free and saves the request

    A number already used by staff is refused: active → "already part of a studio" with a Log in link; deactivated or removed → "used with a studio before". Otherwise a signup request is saved, keyed by the phone digits.

    requestCode() → POST /api/signup/start → findStaffByPhone()upserts signup_requests
  3. A code is sent

    This time Supabase may create the login. The hook allows the code because a fresh signup request exists.

    signInWithOtp({ phone, shouldCreateUser: true })creates auth.users row
  4. The code is verified
    handleVerify() → verifyOtp()
  5. The server creates the studio

    It finds the signup request (less than 15 minutes old), confirms the person isn't already staff, picks the free plan, and creates the organization with a unique slug, the email and the plan's AI credits.

    POST /api/signup/complete → createOrganization()inserts organizations"This signup has expired. Please start again."
  6. The person becomes the studio's admin

    A staff row with role admin is created and the signup request is deleted.

    inserts staff, deletes signup_requests
  7. The admin dashboard opens

    The session is claimed exactly like a login, then /studio/admin opens.

    claim_staff_session → router.push("/studio/admin")admin dashboard

Why it fails openThe staff lookup is limited to 1.5 seconds. If it can't finish, the request continues — the page and the database rules still protect the data.

One device at a time

  1. A new login claims the session

    The newest login's id is stored in staff.current_session_id.

    claim_staff_session()
  2. The old device notices

    SingleSessionGuard listens to the user's own staff row through Realtime and re-checks when the tab is focused. A different session id means this device was replaced.

    SingleSessionGuard.tsxRealtime on staff
  3. The old device is signed out

    It signs out locally and opens the login page with the reason. The proxy also blocks any further request from it.

    "You were logged out because your account was signed in on another device."

Known issues

  • Unfinished signups leave a login behind (reused later if the number is added as a designer).
  • Old signup_requests are never deleted.
  • The Supabase hook is shared with production — pointing it at a local server breaks production logins.

Find a customer

  1. The designer types in the search box

    Every change searches by name or phone. Results only include this studio (database rules).

    designer/page.tsx → supabase.rpc("search_customers", { q })reads customers
  2. No match: the form fills itself

    Digits go into the phone field, letters into the name field, ready to add.

    "No account found" form
  3. A match: the designer picks it

    The page counts the customer's completed sessions and offers Start New Design or History.

    handleSelectCustomer()counts sessions

Add a customer with a phone check

  1. Name and phone are entered

    The same steps exist on the designer dashboard and in the admin's Add Customer pop-up. The pop-up first checks the number isn't already a customer here.

    AddCustomerModal.tsx → handleSendCode()
  2. A code is sent to the customer

    The server creates a 6-digit code valid for 10 minutes and sends it from Stenslee's WhatsApp number.

    POST /api/customers/send-verificationinserts customer_phone_verifications
  3. The customer reads out the code

    The server checks code, phone, studio and expiry, then marks it verified.

    POST /api/customers/verify-phone"Incorrect or expired code."
  4. The customer is saved

    A database trigger only allows the insert if this phone was verified in the last 15 minutes. Phones are unique per studio — the same person can be a customer at other studios too.

    inserts customers (trigger customers_require_phone_verification)
  5. The first session starts (designer flow)

    A session id is generated and a session row is created for this customer, handled by the designer.

    startSession() in app-store.tsinserts sessionsDesign page

Customer profile and history

  1. The profile loads

    Customer details, finished tattoos and in-progress sessions load together. Rework "before" photos are fetched in one batch from the chat history.

    customer/[userId]/page.tsx → load()reads customers, sessions, chat_messages
  2. History cards show before/after

    AI designs show design → placement preview; reworks show the original tattoo photo → new design. Filter by type.

    Tattoo History grid
  3. Edit or start a new tattoo

    Name and phone can be edited (the new phone is not re-verified). + New Tattoo starts a session.

    handleNewTattoo() → startSessionForUser()

Known issues

  • No way to delete a customer.
  • Verification codes are stored in plain text and never cleaned up.
  • Phone edits skip verification.

Start a session

  1. "+ New Tattoo" on the customer page

    The store creates the session row (8-character id, status active, handled by this staff member) and opens the Design page.

    handleNewTattoo() → startSessionForUser()inserts sessions
  2. The Design page loads the session

    If the store already holds this session it skips loading (the store can be ahead of the database); otherwise it reloads it from the database.

    design/page.tsx → hydrateFromSession()reads sessions, chat_messages
  3. Plan features decide which tabs work

    AI Design, Upload Existing, Rework, Camera, Pinterest, Browse Previous, Text Tattoo and Enhance are each checked; locked ones show a lock.

    useFeature() in use-feature.ts

Generate the first 5 designs

  1. The designer fills in the form

    Style (70+), description, up to 5 references, ink colours, body area. Everything goes into the Zustand store.

    localStorage cleopatra-app-store
  2. "✦ Generate Tattoo Designs" opens the chat

    A "pending generation" flag is set and the Chat page opens and starts the batch once.

    handleGenerate() → chat/page.tsx → startGeneration()
  3. References are uploaded from the browser

    Local images are uploaded to {sessionId}/refs/; already-hosted ones are reused.

    uploadPhotoDirect() in browser-upload.tsstorage session-assets
  4. The session and chat are written

    Style, description and body area are saved on the session; a user message and an empty assistant message are created.

    runGeneration(), syncSessionDetails()updates sessions, inserts chat_messages
  5. The server checks the plan and builds the prompt

    requireFeature("ai_design") must pass. The prompt comes from buildTattooPrompt(); the model is gpt-image-2-image-to-image.

    api/generate/route.ts → POST()"description is required", plan limit messages
  6. Credits are reserved, the job starts, the server answers

    10 credits per image are reserved (fewer images if the balance is low). A job with 5 pending slots is stored in memory and the server replies at once.

    reserveCredits(), startJob()organizations.ai_credits_remaining"Out of AI credits"
  7. 5 KIE tasks run in parallel

    rotateReferences() gives each slot a different leading reference. Each task is polled every 3 s; finished images are downloaded and stored on the job. Failed images refund their credits.

    runOneTask() → createKeiTask() / waitForKeiTask()
  8. The browser polls and saves each image

    Every 5 s it asks for the job. Each new image is uploaded to {sessionId}/designs/ and added to the assistant message. Usage is logged once per batch.

    watchJob() → /api/generation-statuschat_messages.image_keys, usage_logs5 designs appear one by one

Refine in chat

  1. Select images and write the change

    Pick one or more designs, type the change ("thinner lines") and choose 1–5 new images (default 2).

    toggleSelect(), handleSend()
  2. A refinement request is sent

    The instruction replaces the description, the selected images are the inputs, and faithfulMode can limit it to minor changes. The "needs a reference" rule is skipped.

    runGeneration() → /api/generateusage_logs action refinement_round
  3. Results join the same chat

    Same job + poll flow. Every batch stays in the thread to compare; the viewer flips through all images.

    new batch under the instruction

Text tattoo

  1. Turn on Text Tattoo mode

    A typography pop-up loads curated, system and Fontsource fonts.

    TypographyGenerator.tsx
  2. Type the words, pick a font, add to references

    The lettering is drawn on a canvas, exported as PNG and uploaded as a reference.

    handleTypographyGenerated() → /api/upload-refstorage designs
  3. Generate with the lettering model

    Same flow, but the server uses nano-banana-pro and the text-tattoo prompt; text_tattoo must be on the plan.

    /api/generate with isTextTattoo

Enhance with AI

  1. Tap "Enhance with AI" under the description
    POST /api/enhance-prompt with description + style
  2. OpenAI writes three better versions

    The server calls gpt-4o-mini and returns the variations; usage is logged.

    "OpenAI API key not configured", plan limit
  3. Pick one
    description replaced

References: Pinterest, camera, upload

  1. Pinterest search

    The server asks Pinterest's internal search endpoint, cleans the results and returns pins; thumbnails load from Pinterest.

    PinterestSearch.tsx → /api/pinterest/searchusage_logs pinterest_search
  2. Picking a pin

    The image is fetched through /api/pinterest/image, shown at once, then saved permanently to refs in the background.

    addPin() → handleAddPinterestPin()
  3. Camera or files

    Files (jpg/png/webp/heic, up to 5) or a camera photo are kept in memory and uploaded when Generate is pressed.

    useDropzone(), CameraCapture.tsx → usePhoto()

Upload existing or browse previous

  1. Upload or photograph a ready design

    The file is uploaded to designs and skips AI generation.

    handleDirectFileDrop()
  2. Or pick a previous design

    A pop-up lists finished designs the user may see (designers: their own), filterable by customer or designer.

    PreviousDesignsModal.tsxreads sessions.selected_design_key
  3. "Proceed to Placement"
    handleProceedDirect()Placement page

Rework and the flash version

  1. Photo of the old tattoo + cover or extend
    handleGenerateRework()
  2. The photo is uploaded and the batch starts

    Photo to rework-source; the server uses the rework prompts and gpt-image-2-image-to-image; same credits, job and poll flow.

    /api/generate-reworkusage_logs via rework
  3. Edit rounds

    Selected results plus an instruction go back to the same route.

  4. Finalize starts a flash (white-background) version

    The chosen design is isolated on white for stencils; the session overview saves it when ready (and offers a manual retry).

    startFlashGeneration() → /api/generate-flashsessions.flash_image_key

A page reload during a batch

  1. The server keeps working

    The job lives on the server, not in the browser request.

  2. The chat asks once if a job is running

    If the job exists, isn't done and the last message is the assistant's, polling resumes and finished images are saved.

    load() → /api/generation-status

Known issues

  • generation-status, upload-ref, proxy-image, pinterest/image have no login check.
  • Jobs are kept in server memory (one server only); Pinterest uses an unofficial endpoint.
  • The store (with customer name and phone) stays in localStorage after logout.

    From the chat, upload or previous designs, the design is stored on the session and Placement opens.

  1. Describe the spot, or switch to Upload / Camera

    Quick chips (forearm, back…) or free text; switching modes clears the other inputs.

    handleModeChange()
  2. The editor places the design in the centre

    Drag to move, corner handle or wheel to resize, top handle to rotate.

AI preview generation

  1. Images are uploaded

    Composite to composites, original photo to body (photo path only).

    handleGenerate() → uploadBase64Direct(), uploadPhotoDirect()

Stencil download

  1. Session details offer Download

    The printable image is the flash version (rework) or the chosen design.

    SessionOverview.tsx
  2. The print studio sets defaults

    1 sheet, A4, PDF, 2 mm margin; the design is trimmed of empty edges.

    TattooPrintStudio.tsx, loadTrimmedStencilImage()

    Large designs split across pages; the image is mirrored for transfer.

    computeStencilLayout()
  4. PDF or image download

  • Body photos live in a public bucket.
  • Permanent delete misses rework, rework-source and flash files.

    restoreLibraryFile()

    The storage object and row are removed.

    purgeLibraryFile()

Known issues

  • Automatic purge never runs (cron misconfigured); trashed files keep using quota.
  • The bucket is public.

Connect a number

  1. The page checks the connection

    Not connected → the Connect button; connected → number, templates and sending.

    whatsapp/page.tsx → loadConnection()reads organizations.whatsapp_*
  2. The button loads Meta's SDK and listens for messages

    Facebook JS SDK v23.0 is loaded once; the page listens to the popup's postMessage events.

    loadFacebookSdk(), handleMessage()
  3. "Connect to WhatsApp" opens Embedded Signup

    FB.login with the login configuration and extras version v3, featureType whatsapp_business_app_onboarding (Coexistence). Detailed [whatsapp-connect] logs are printed for debugging.

    handleConnect()
  4. The admin completes Meta's popup

    Logs in with Facebook, picks the business, types the number. A Business-app number is confirmed by a QR/message in the WhatsApp Business app.

    "Ineligible" / #2655111 until Meta approves the app
  5. Two halves arrive, in any order

    The finish event (FINISH_WHATSAPP_BUSINESS_APP_ONBOARDING = Coexistence, FINISH = normal) and the one-time code. When both are in, the server is called.

    checkBothReady() → POST /api/whatsapp/connect/callback
  6. The server checks plan and role, swaps the code for a token
    requireFeature("whatsapp"), exchangeCodeForToken()
  7. Webhooks are subscribed and the number found
    subscribeWabaWebhook(), listPhoneNumbers()"No phone number found on this WhatsApp account"
  8. Coexistence syncs or number registration

    Coexistence: request smb_app_state_sync and history (required within 24 h; the data is dropped). Normal number: register it for sending.

    requestSmbAppSync() / registerPhoneNumber()
  9. The connection is saved

    WABA id, phone id, display number and the access token (plain text for now) are stored; the page shows Connected.

    updates organizations"Connected" with the number

Disconnect

  1. "Disconnect" clears the connection fields
    handleDisconnect() → DELETE /api/whatsapp/connect/callbackclears organizations.whatsapp_*
